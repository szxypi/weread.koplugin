本轮先验证真实接口，再决定是否接入新的公众号功能。
当前账号的书架返回两个公众号，目录 `/web/mp/articles` 均返回 HTTP 200、业务码 `-2041`。
执行一次已有 Web 授权续期协议后，续期响应为成功，同账号回查和钥匙串保存回读通过，
但响应没有 `x-wr-ticket`／`x-wrpa-0`，两个目录仍返回相同业务码。
[去敏实测记录](validation-assets/2026-11-09/mp-web-renewal-catalog-owner.json)没有保存账号、公众号 ID 或原始响应。

这不证明再次扫码会解决目录验证，也不证明真实公众号目录、分页或订阅已通过。
没有继续循环续期，没有执行书架、阅读进度、时长、批注或其他账号数据写入。
新增公众号目录功能仍待取得可验证的服务端响应，不用合成成功数据替代真实接口验收。

## 正文读取的独立证据

使用仓库已有验证脚本中的已知文章样本，通过 `/web/mp/content` 取得正文页面。
Python 按现有 Lua 的正文提取规则计算内存投影，Lua 对同一响应的投影一致；
KOReader 原生 HTTPS 再独立 GET 一次，提取结果也一致。
同一次原生验证另独立读取两个目录，两者同样为 `-2041`；原生请求总计三个 GET，没有续期 POST。
[去敏记录](validation-assets/2026-11-09/mp-content-owner-readonly.json)仅保留状态和布尔值，
正文、正文摘要、文章地址、会话头及 Cookie 均不进入报告或文件。

该结果只证明这个正文样本与既有提取器的一致性，不证明公众号目录、
微信文章链接导入、所有正文类型、图片打包、订阅或导出已经完成。
后续已独立补齐[缓存文章导出 EPUB](mp-article-export.md)，分别记录真实只读转换与合成原生打包证据；
这不改变本节的目录未通过结果，也不把订阅或文章链接导入标为完成。
后续[文章缓存身份与链接前置检查](mp-article-cache.md)补充了同名缓存保护；一个匿名规范化源链接返回 302 验证路径，
未跟随跳转，也没有将链接导入接入 Lua。
没有将真实正文导入插件配置，也没有为验证生成真实文章文件。

## 凭据维护与保存

开发验证继续使用原有两个 macOS 钥匙串条目，不创建第三个条目或凭据文件。
Web 条目兼容原 Cookie 格式，并增加可选的附加授权头、修订和续期待确认状态。

- 续期前先保存并回读待确认标记，再最多提交一次固定凭据维护 POST。
  超时、未知回执或重复调用不重发；新进程也会读取标记并拒绝重复提交。
- 成功回执之后核对同账号，才能提交更新后的 Cookie／附加头并清除标记。
  账号或凭据修订已被替换时，旧续期结果不能覆盖它。
- 普通只读验证在 Cookie 权限未变化时保留已有附加头和待确认标记。
  已核对的新 Cookie 权限推进修订并替代旧待确认状态，同账号既有附加头继续保留；
  续期响应缺失某个附加头时沿用旧值，不把“没有返回”当作主动清除。
  现有条目读取失败时停止保存，不覆盖未知内容。
- 只允许两个有界附加字段；不保存错误原文、其他响应头或正文。
  实际本次响应缺少这两个头，没有宣称真实附加授权已取得或已恢复目录。
- 这里的待确认保护属于本机 Python 开发验证工具；不等同于 KOReader 中 Web 续期协调已完成。
  插件原有墨水屏授权的独立续期状态机保持不变。

开发授权继续保留，直到整体目标完成或用户撤销授权。

## 插件中的具体修正

现有公众号读取遇到 `-2041` 后，仍按原有流程最多刷新一次凭据并重读一次。
如果仍失败，现在提示“公众号验证暂不可用，已缓存文章仍可阅读，请稍后重试”，
不再一概提示重新扫码；原有 `-2012` 登录错误的引导保持不变。
目录、正文及该 Web 续期路径的敏感失败诊断只保留阶段／状态，
不把错误正文、查询参数、附加响应字段或底层异常带入日志和提示。
不改变这些接口的请求地址和有效数据处理方式。

600×800 和 KO2 1264×1680／300 DPI 的完整原生核心流程验证：
成功但没有附加头的续期之后，目录仍失败时显示正确原生提示，保留 Cookie，
仅一次续期／两次目录读取，不自动启动新二维码，也不留下等待窗。
同时回归普通阅读链接导入、书架／书城／资料／统计、授权、下载、原文导航和离线时长。
[运行记录](validation-assets/2026-11-09/mp-verification-runtime.json)与截图只使用合成数据；
这不代表实体 KO2 验收。

## 复验

默认离线，不访问钥匙串、账号或网络：

```sh
python3 scripts/verify_mp_catalog.py
python3 scripts/test_mp_catalog.py
python3 scripts/test_secure_weread_session.py
luajit spec/client_spec.lua
luajit spec/library_cache_flow_spec.lua
```

显式复用保存的授权，仅读两个现有公众号的目录：

```sh
python3 scripts/verify_mp_catalog.py --saved-session
```

可显式添加 `--renew-web` 做一次凭据维护；它不是账号数据写入开关，
也不会在目录仍失败时循环续期。当前实际目录验证未通过，因此命令返回非零。

正文模型与原生 HTTPS 对照，不再续期：

```sh
python3 scripts/verify_mp_catalog.py --saved-session --check-content --lua-command \
  docker exec -i -e XDG_RUNTIME_DIR=/validation/source-binding-xdg \
  -w /validation/runtime/lib/koreader weread-validation xvfb-run -a \
  ./luajit /source/spec/koreader/mp_content_probe.lua /source
```

即使正文对照通过，目录仍失败时报告保留 `MP_CATALOG_UNVERIFIED`，不会用正文成功覆盖它。

目录读取现已将既有首批 GET 移到后台，每次刷新只读一次，不再自动续期并重读。
取消／账号与会话保护、失败恢复保存列表、有效空目录及满 100 篇提示已接入；
成功、空目录、分页控件与存储回读仍只由合成数据验证，不改变真实 `-2041` 的未通过结论。
见[后台目录说明](mp-article-catalog.md)。

原生入口另已接入[Web 续期与读取恢复](web-authorization-renewal.md)：目录／正文的登录失效最多完成一次确认后的读取恢复，
`-2041` 不自动续期，真实成功目录仍未验证。固定续期协议在 Python 与插件 HTTPS 各独立验证一次，
均完成同账号核对、139 本书架及钥匙串保存回读；自然过期和真实限频不据此标为通过。
