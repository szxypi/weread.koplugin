# TXT 定时同步与本机保存失败恢复

开发分支的原生 TXT 通道支持一分钟至六十分钟的定时同步。只有已在线核对过云端、当前原文点明确且本机有新移动时才计时；不会补发错过的周期。定时到期后再次读取云端，其他设备已改动时转为显式选择。

## 云端成功但本机保存失败

原生服务先把明确成功回执和独立位置核对结果保存到账号 SQLite，再交给阅读状态保存流程。若后者失败：

- 停止当前定时任务，清除本次自动同步资格，保留本机移动和未保存的意图。
- 显示“微信读书已确认上传，但本机结果未能保存”，提示检查存储并再次同步核对。
- 不接受或清除持久确认记录，不把云端成功说成未知，也不会自动重发该请求。
- 只读相等确认的保存失败使用单独提示，不声称曾执行上传。提示本身失败也不改变上述收尾行为。

再次点击普通“同步进度”，进入[待确认记录核对](native-position-review.md)。后台两次读取完整原生状态；归档保留真实阶段、原编号和状态哈希，不保存正文摘要。最新本机移动继续保留，重新比较有差异时仍需选择。

取消或进入核对会释放先前交付留下的内存回执，持久记录保留。这避免旧句柄在记录已经归档后继续阻塞新请求。使用云端进度只重新核对来源、定位并保存比较结果。

## 独立验收范围

新工具 `scripts/verify_native_timer_trial.py` 默认离线。真实运行使用独立钥匙串范围和协议，不复用手动、关书或其他已消费试验；旧范围仍参与全局未完成任务检查。

准备阶段在网络发送前阻断请求，绑定实际阅读器生成的整数显示百分比，零数据修改。正式阶段最多两次零时长位置请求：

1. 原生阅读器先在原点完成只读一致比较，再移动到同章后一字，生产定时器自然等待一分钟。宿主独立计时，拒绝提前申请发送；不替换真实时钟或提前调用任务。
2. 第一次明确成功并独立回读后，仅让本机阅读状态提交失败。验证 SQLite 确认记录、本机意图、错误提示和定时器停止。
3. 恢复本机保存，产生新的本机移动，沿普通同步入口核对、归档并重新选择云端。核对使用真实后台进程和六次只读请求；旧请求保持一次，归档阶段为 `verified`。
4. 用新的来源证明和独立请求恢复钥匙串中的完整原位置／原摘要，独立核对后封存两个发送槽。最后只读同步和原文／目录／计数／书架核对，不产生第三次修改。

每次发送前先持久声明槽位；成功回执先持久保存再继续核对。异常或中断停止，不自动重跑、恢复或续期。原始凭据、摘要和来源仅在钥匙串、内存管道和临时内存文件系统中；普通记录只包含固定字段。

模拟服务已在 600×800 与 KO2 尺寸验证完整流程，另有自然等待一分钟的模拟运行。真实账号 600×800 流程也通过：宿主独立计时 64 秒、生产定时器到期 61 秒，两次明确成功回执及两步独立核对；完整原位置／摘要恢复、三项计数与可见书架保持，授权 POST 为零。两槽已封存，旧手动／关书范围与原生授权未改变。全量 255 组 Lua、123 个 Python 文件共 1579 项测试（零跳过）通过。结果及全量回归见[固定字段验收记录](validation-assets/2026-11-12/native-timer-recovery.json)。

实体 KO2、实际设备磁盘写满／断电、多设备并发改变与更多格式仍待验收。定时验证不代表阅读时长功能已完成，设备性能专项仍在整体功能验收之后。
