# 真实原生划线保存与删除

修复后的生产原生流程已经完成一次真实两步：实际书架进入原文阅读，选中文字并确认保存划线，
宿主完整回读后，再从本人云端划线列表删除该记录并完整回读。
本次生产代码为已通过 CI 的 `6e16d4b`，候选 241 个文件与源码及实际安装内容逐字节一致。
使用官方 KOReader v2026.07.1 Linux ARM64，1264×1680／300 DPI，没有网页界面或实际截图。

## 实际结果

- 恰好两次原生账号数据 POST，创建与删除各一次；宿主没有账号数据 POST，没有写入重试或本次授权续期。
- 启动前独立钥匙串意图一次占用两个额度，原生 SQLite 记录和测试门槛在可能发送前提交。
- 创建后和删除前，宿主两次完整读取均确认唯一测试划线与所选章节描述存在；原有集合、书架标记及原生位置符合基线。
- 删除后和最终检查，宿主两次完整读取均确认测试划线与该章派生索引消失，所选章节没有剩余标记。
- 生产规则正确确认这次删除，没有停留 pending；原生缓存、原有云端集合、两通道精确位置均与基线一致。
- 原生控件、后台任务、界面心跳、原文位置往返、原生笔记不变、凭据文件审计与工作进程回收全部通过。
- 测试意图清除后，新实例再次确认不存在；私有 tmpfs 配置已删除，Linux 进程和私有目录再次检查为空。

本次所选书籍原有划线与本人想法均为零。非空原记录及并发变化的保护已由两尺寸封闭合成流程覆盖，
这次真实空集合不替代非空集合、其他范围／格式、多设备或实体 KO2 验收。
服务端排序、历史和未返回字段不属于完整恢复保证。

## 首轮发现与独立接续

最初候选派发过两次原生请求，但由于服务端移除了最后一条划线的章节索引，旧规则没有确认删除。
执行器立即停止，没有重发；随后只读完整重建原计划，确认测试目标已消失、原状态及原文／目录／位置完全一致，才清除本机意图。
另一个独立 Python 两次实验捕获真实索引生命周期，Python／Lua 的旧失败规则一致，复现并定位问题。
修复只放行「目标恰好消失、同章无剩余标记、所选描述消失、其他描述与本人想法未变」的情况，见[修复说明](highlight-last-mark.md)。

修复候选预演前遇到明确 HTTP 401，零数据写入及零占用额度。
仅进行一次保存式授权维护，核对同账号书架与钥匙串回读，再重新完成真实禁止发送预演。
当前两步使用新的完整计划和一次性启动记录，没有重跑旧意图或退回已占用额度。
原 Web／墨水屏登录按用户要求继续保留到整体目标完成。
