# TXT 实际阅读器的原生写入验证

打包插件已经在真实账号中通过一次正常手动同步写入，再通过独立恢复流程还原原始完整位置和摘要。
首次修改走实际 ReaderUI 的“同步→保留 KOReader 进度”，使用生产 `SourceUpload`／`ProgressSync`，
第二次使用原生位置服务恢复已保存的原状态。两次均取得明确成功回执，每步均由宿主另行读取核对。
这证明该场景的手动发送，不能扩展为关书上传、全部 TXT、其他格式或实体 Kindle 已验收。

## 新范围与请求边界

本次使用独立钥匙串协议 `native-reader-literal-raw-30-zero-time-v1`，最多两个修改槽位。
旧原文摘要、通用面板及 Python 往返试验不复用，其已消费／未验证结论保持。
全局试验检查会拦住其他未收尾试验，仅本范围的准备、发送与只读恢复可以排除自己的记录。

准备阶段在实际阅读器定位原位置后一单位，核对 UTF-16 坐标和原始 TXT 的 30 个 Unicode 标量，
由独立 Python 模型核对原文摘要、目录、完整请求体及签名。百分比绑定当时阅读器的整数显示值，
不根据原文字节数估算，也不要求它与上次云端百分比相同。初次禁止发送预演中观察到该值后，
完整原位置、目标、计数、来源／目录／书架／授权指纹才保存为准备记录；正式发送不得改写该百分比。

实际派发前先持久领取本次槽位，成功回执先持久保存，再释放下一步独立核对。
重复领取、缺失回执、来源变化、时长变化或异常均停止，不自动续期或重发。
生产本机状态先保存，再接受第一步完成回执；恢复另行准备原位置的在线来源证明，
使用钥匙串中完整的原摘要，避免以重新生成的字面片段替代 App 原摘要的空白形式。

恢复工具仅针对本协议的剩余槽位与完整已知绑定，不为已消费试验创造新额度。
只读收尾保留明确的已消费结论；未知结果不当成协议成功。

## 本次证据

[固定字段验收记录](validation-assets/2026-11-12/native-reader-trial.json)不含书籍身份、正文、坐标、凭据或原始响应。

- 两尺寸模拟器均通过准备、实际 ReaderUI 手动发送、完整原位恢复和两步独立回读；每套两个合成 POST。
- 真实账号先完成一次禁止派发预演，核对实际生成请求体并拦截发送，零修改、零领取。
- 600×800 实际阅读器正式流程恰好两个原生 POST、两个明确成功回执、两步独立核对；
  原完整位置／摘要恢复，三项时长计数和可见书架标记／分组保持。恢复后又重新读取来源、目录、元数据和原状态。
- 正式流程无 Web 修改、授权 POST 或历史时长记录。短期配置／正文只放内存文件系统并已删除，
  278 个安装文件与候选／源码一致，文档只在父进程访问，子进程已回收，实际凭据文件审计通过，无正文截图。
- 新范围现为 `retired`、两槽均消费；独立启动标记也已消费。凭据按约定继续留在钥匙串。

只确认接口可见的完整位置、摘要、计数和书架状态，未声称还原服务端历史、排序时间或未返回的字段。
真实定时发送、关书独立交接、待核对回执恢复界面、更多边界和实体 KO2 仍需继续验收；
