# 旧共享阅读记录的恢复原型

旧 HTML 的共享记录现在有了明确的失败与恢复证据；产品中的恢复入口仍未实现。
本工具只在新建的合成配置中运行，不读取用户日常配置、账号、凭据或真实笔记。

## 已复现的丢失路径

官方 KOReader v2026.07.1 对两份等长旧 HTML 的抽样哈希可能相同，即使中段文字不同。
共享记录的主文件和 `.old` 备份可以分别保留不同的位置、书签、划线及附注。
从哈希保存切换为随书保存后，实际打开其中一份原文，可能加载另一份的位置与笔记；
正常关书触发 KOReader 迁移，同时清理共享主文件及备份，另一份原文失去可读取的记录。

600×800 和 1264×1680 两种尺寸均复现上述过程。
这不是新版本标记失效：当前下载管线已经隔离新文件，问题存在于此前没有独立标记的旧 HTML。
当前「已保存版本」仍把旧文件直接交给 KOReader；不能把“文件仍在列表中”当作共享记录可安全迁移的证据。

## 本次验证的恢复方式

1. 在隔离 ReaderUI 中分别保存两份原文的位置、原生书签、实际 CRE 范围划线及附注。
   人为推进主记录的修改时间，仅用于让 KOReader 的正常备份规则留下两份不同的测试记录。
2. 保留共享主文件和备份的原始字节。测试夹具明确指定每份正文要用哪个记录，
   不按 `doc_path`、修改时间或标题自动推断真实归属。
3. 保持原文和原记录不变，另外建立 HTML 副本，仅在头部加入独立标记。
   新副本的哈希必须与旧文件不同，且不能已有阅读记录。
4. 通过 KOReader 的记录对象把显式选中的数据写入新副本的独立位置。
   这一步没有把共享记录直接迁移或覆盖到原文件。
5. 实际打开、绘制和关闭恢复副本，核对正文版本、位置可见性、书签、划线和附注。
   每次关闭后重新读磁盘配置，确认公众号容器的本机进度和待上传记录不变。
6. 再对原文件执行会删除共享记录的对照操作，证明独立副本仍能重开；
   退出后另启全新进程再次打开全部恢复副本，核对原文和保留快照的字节未变。

每种尺寸覆盖主记录／备份与随书／集中目录／哈希三种目标位置，共 6 份恢复副本。
恢复阶段实际打开 15 次，独立进程再打开 6 次；两尺寸合计 42 次 ReaderUI 打开、12 份恢复副本。
另外用不加新参数的原工具完成 54 次正常位置迁移／新进程重开，原默认路径继续通过。
三份候选包各 174 个安装文件均与生产源码及安装目录逐字节一致，ZIP CRC 通过，零重绘失败。
本地测试服务收到的请求为零。公开[原生记录](validation-assets/2026-11-09/mp-legacy-record-recovery-runtime.json)
仅含合成状态、数量、尺寸与源码标识，不含文章、笔记、坐标或配置文件。

## 产品接入仍需完成

- 原生入口应让用户明确选择正文版本和可恢复记录，展示主记录／备份、笔记预览与恢复范围。
  已经被覆盖且没有保留副本的数据不能凭标题或时间重建。
- 在打开可能共用记录的旧缓存前保留可回读快照，包括当前阅读器尚未关书的记录；
  保护数据应放在独立存储，不能放进小型配置或修改共享原记录。
- 复制与保存完成之后才切换当前版本；取消、换账号、切书、缓存替换、空间不足及提交失败不能删除原记录。
- 需补齐恢复界面、后台任务、并发保护、失败回退和记录存储验证；
  本工具没有实现这些产品行为，也不证明旧 EPUB、任意内容差异、整机断电或实体 KO2 已通过。

当前可证明的是合成数据下显式选择记录后的独立恢复路径，不能据此标记完整旧记录恢复功能已完成。

## 重现

只能指定尚不存在的运行目录，工具会拒绝复用已有目录并创建新的合成配置：

```sh
xvfb-run -a python3 scripts/test_mp_metadata_runtime.py --legacy-shared \
  --koreader /path/to/runtime --run-dir /path/to/new-run \
  --width 1264 --height 1680 --dpi 300
```

不传 `--legacy-shared` 时，仍执行原来的六种正常保存方式切换验证。
工具使用 `spec/koreader/mp_legacy_metadata.lua` 的原型，没有启用插件中的新恢复菜单。
