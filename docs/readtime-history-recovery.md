# 历史时长的只读恢复与真实跨日采集

[上一阶段](readtime-transfer-queue.md)的历史请求没有核实入账。本轮未提交任何新时长，
也没有再次发送旧请求；新增可重复使用的只读诊断工具，并保存一条真正经过计时的测试窗口，
等待不同日期后再作独立预检。历史补传仍未启用。

## 结果不明的旧请求

`verify_readtime_recovery.py` 默认离线；指定 `--saved-session` 才读取本机已保存登录。
它只允许目标书籍进度和对应历史月份统计的四次原生 GET，另外由既有来源工具完整核对
目录、原文、原标记／想法、书架标记和 Web／原生精确位置。两轮读取间隔两秒，
计数和统计均须与旧意图的基线摘要一致；额外秒数、位置变化、超时、账号变化或意图替换均停止。
它没有时长发送、续期或重试写入路径；Web 内容工具已有的只读 POST 不算账号数据修改。

先运行只读诊断，通过后再运行一次本机封存，实际均通过：

```bash
python3 scripts/verify_readtime_recovery.py --saved-session
python3 scripts/verify_readtime_recovery.py --saved-session --retire-unverified
```

封存保留完整原计划、已消费次数和独立诊断摘要，只将钥匙串条目标为 `retired`。
它仍是 `UNVERIFIED`，不能改成已验证、删除收据、重新领取或恢复旧发送额度。
这只表示结束该次试验的活动占用，不证明服务端永远不会延后入账。
两次实际运行均零账号数据修改、零授权请求；原记录、精确位置、逐书计数和月度统计一致。
原先首轮缺少统计基线的 v1 封存也继续独立保留。

## 真实采集后等待跨日

前一日失败样本是人为回拨时间的控制窗口；只靠当前日期的成功，无法判断服务端是否按历史小时入账。
新的 `verify_readtime_history_capture.py` 读取当前来源、原生／Web 目录版本和逐书计数，
实际经过两秒后再读取，使用墙钟与单调计时共同核对。它不编辑已采集时间、不构造发送载荷，
不预约 HTTP 次数，也没有领取／发送方法。它仅把一份有界的来源摘要保存在钥匙串中。

```bash
python3 scripts/verify_readtime_history_capture.py --saved-session
python3 scripts/verify_readtime_history_capture.py --saved-session --status
```

实际采集通过：前后版本、逐书计数及原记录／精确位置一致，账号数据和授权请求均为零。
该控制窗口仍不是实体 Kindle 的本机阅读账本，不应描述为已上传的离线阅读。
它最早在 **北京时间 2026-11-13 00:00:01** 后进入另一套跨日预检，当前没有安排自动发送。
新进程能读取同一份记录；再次采集不能替换它，记录本身也不代表已经验证了历史入账。

后续预检需重新核对捕获的来源、版本、设备身份和计数，再绑定新的发送载荷、独立月／日基线和
一次持久领取。只有历史日期的准确两秒增量与其他计数、桶及原记录一起核对通过，
才可继续历史发送任务；不能接受总数增加却落在当天，也不能重发旧的未确认请求。
当前尚未实现这一步，也未将新规则提前移植到原生网络层。

官方客户端的补传准备会先核对云端进度，在另一设备的位置更新较新时省略旧位置；
该本地逻辑没有给出服务端历史时长的入账期限。此处只记录静态发现，不据此推导服务端条件。
安装包来源和指纹见[前次静态核对](readtime-transfer-queue.md#官方客户端静态核对)。
